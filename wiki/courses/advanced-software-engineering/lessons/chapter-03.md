# 第三章｜需求工程

> 依講義重新整理；頁碼一律指 PDF 頁次。例子標為自編；整理稿尚待使用者複核。

## 本章主線：把期望變成能驗收的規格

**Requirements Engineering（RE）需求工程**把利害關係人要的服務與限制，轉為可理解、可協商、可實作及可驗證的描述。越晚發現需求錯誤，越可能重做架構、程式、測試與部署。講義的 100 倍曲線用來強調晚改的代價，本頁不把該倍率當所有專案通則。[ASE-003，PDF p.5–9、54、59]

## 3.1 需求層次與分類是兩個問題

| 層次 | 讀者與重點 | 自編例 |
| --- | --- | --- |
| User Requirements 使用者需求 | 使用者／主管，較高階的服務意圖 | 學生可以查詢可加選課程 |
| System Requirements 系統需求 | 開發與測試人員，精確行為與限制 | 查詢依課號回傳班級、時段與剩餘名額 |

來源：[ASE-003，PDF p.8–11]。分享對話中的 Business → User → System 是**抽象層級**的題型；Business 表達組織目標。此延伸用來理解範例，不要將它與下方「功能／非功能／領域」混成同一分類。[EXAM-001，分享對話試題23；ASE-003，PDF p.8–9]

| 類型 | 問的是什麼？ | 自編例 |
| --- | --- | --- |
| Functional Requirement（FR）功能性需求 | 系統提供什麼服務或反應？ | 系統可在學生加選時檢查先修資格 |
| Non-Functional Requirement（NFR）非功能性需求 | 品質、流程或其他限制？ | 在指定負載下，95% 查詢兩秒內完成 |
| Domain Requirement 領域需求 | 哪些要求來自業務、環境或規範？ | 學校規定未通過先修不得加選 |

來源：[ASE-003，PDF p.8、15–18、20]。領域需求描述**來源與背景**，可能落實為功能或非功能限制；判讀時不要只因出現數字就說一定是 NFR。上表門檻為自編示例。

## 3.2 利害關係人與衝突

**Stakeholder** 不只使用者，還包含管理者、維運、安全、外部監管與其他受系統影響的人。訂餐消費者想隨時取消、餐廳想確保已備餐能獲補償，必須協商條件與責任，而不是兩句都照收。[ASE-003，PDF p.13–16]

常見需求問題有：語意模糊（取消是否代表退款？）、完整性不足（漏了付款失敗）、一致性不足（同一情境同時允許及禁止）。解法是釐清名詞、條件、例外與優先順序，持續精煉，而非期待第一次訪談就完美。[ASE-003，PDF p.16、33–34]

## 3.3 非功能性需求三大家族

| 家族 | 英文 | 辨識線索 | 自編例 |
| --- | --- | --- | --- |
| 產品需求 | Product | 交付產品的品質 | 查課延遲、可用率 |
| 組織需求 | Organizational | 組織內部政策與開發規範 | 公司要求所有變更經 PR 審查 |
| 外部需求 | External | 法規、監管、外部環境與倫理 | 題目要求符合 HIPAA 隱私規範 |

來源：[ASE-003，PDF p.22–24]。**判斷關鍵是要求的來源**：題目明說「法律規定」，優先辨識 External；不能因它談安全就只回答 Product。這是課堂分類練習，不提供實際法律合規判斷。

## 3.3 延伸：將 Goal 寫成可驗證 NFR

「系統很快、很好用」是目標（Goal），尚缺測量方法。可驗收陳述至少交代**對象／情境、負載或資料量、測量指標、門檻與觀察期間**。[ASE-003，PDF p.25–28；欄位清單為整理]

| 模糊目標 | 自編可測試示例 |
| --- | --- |
| 查詢要快 | 於 100 名同時使用者、指定測試網路下，95% 查課請求兩秒內收到完整結果 |
| 系統穩定 | 以每分鐘探測核心 API 計算，月服務可用率至少 99.9%；維護排除時段需另外定義 |
| 容易學 | 首次使用者接受 20 分鐘教學後，至少 90% 能在五分鐘內完成查詢與加選任務 |

以上數值皆為自編，不是教師指定標準。只寫 p95 而未定測量邊界，或只寫可用率卻未定計算方式，仍可能產生驗收爭議。

| 品質 | 英文指標 | 用途 |
| --- | --- | --- |
| 速度 | TPS、p95 / p99 Latency | 每秒交易量、延遲分布 |
| 容量 | RAM / Disk usage | 記憶體與儲存占用 |
| 易用性 | Training time、錯誤／求助次數 | 學習與操作負擔 |
| 可靠性 | MTBF、Availability | 故障間隔與可用程度 |
| 恢復能力 | MTTR | 故障後恢復所需時間 |
| 可移植性 | 支援平台數、平台相依程式比例 | 換環境所需調整 |

來源：[ASE-003，PDF p.27]。指標不能互換：高 TPS 不等同低延遲；MTBF 與 MTTR 分別關心故障間隔與修復時間。

## 3.4 需求擷取與分析

需求工程包含 Elicitation & Analysis、Specification、Validation、Management，四者交織疊代。不要與「四種擷取技術」混背。[ASE-003，PDF p.34–35]

| 技術 | 最能取得什麼？ | 限制與適用判斷 |
| --- | --- | --- |
| Interviews 訪談 | 目標、理由、主觀痛點 | 可能說不出習以為常的操作 |
| Workshops / JAD 工作坊 | 多方協商與共識 | 要防少數人壟斷發言 |
| Ethnography 民族誌／現場觀察 | 內隱知識、實際工作與非正式捷徑 | 花時間，須觀察真實脈絡 |
| Scenarios / Stories / Storyboards | 具體旅程、正常與例外路徑 | 不可因此漏掉全系統 NFR |
| Document Analysis 文件分析 | SOP、舊系統、表單的業務規則 | 舊規格可能已過時 |

來源：[ASE-003，PDF p.36–43]。講義將訪談與工作坊合為一類，故圖上稱四種技術，本表為比較拆成五列。

訪談要問「為什麼需要這件事」；客戶說想用區塊鏈，先探究是否真正需要防竄改與稽核。**5 Whys** 是深入原因的手法。觀察則回答「他實際如何工作」：這是 Ethnography 能補足訪談的地方。[ASE-003，PDF p.37–38、44–45]

## 3.4 延伸：從故事到使用案例

**User Story** 常用「身為某角色，我想要某能力，以便達成某價值」；**Given–When–Then** 把情境、事件與可觀察結果連起來。它不是只把句子分三行，Then 必須可判定。[ASE-003，PDF p.39]

自編例：Given 學生在選課時段內且已修畢先修；When 申請仍有名額且不衝堂的課程；Then 系統新增選課紀錄並將名額減一。另須補名額已滿、重複送出等例外。

**Scenario** 是一次具體執行路徑；**Use Case** 統整同一目標的成功、替代與例外情境。圖只顯示參與者、功能與關係，文字規格還要有前置條件、後置條件、主要流程與例外。[ASE-003，PDF p.46–51]

Actor 位於系統外；Use Case 用橢圓；System Boundary 用矩形。必要共用功能用 include，條件式擴充用 extend，箭頭詳見第四章。[ASE-003，PDF p.47–50]

## 3.5 五項需求檢查

| 檢查 | 英文 | 要問的問題 | 自編錯誤例 |
| --- | --- | --- | --- |
| 有效性 | Validity | 是真正需要的功能嗎？ | 給醫師做用不到的排班報表 |
| 一致性 | Consistency | 條文互相矛盾嗎？ | 同一時間可取消也不可取消 |
| 完整性 | Completeness | 漏了服務、限制或例外嗎？ | 沒定義扣款失敗 |
| 現實性／可行性 | Realism | 資源與技術上做得到嗎？ | 有限預算卻要求不可能期限 |
| 可驗證性 | Verifiability | 能客觀判定通過嗎？ | 只寫「超級順暢」 |

來源：[ASE-003，PDF p.54–56]。**條文衝突選 Consistency；漏情況選 Completeness；不可測選 Verifiability**。一段需求可能同時有多個問題，單選題需辨認其指定焦點。

## 3.5 延伸：追溯與變更管理

為需求建立唯一 ID，連到設計元件、程式與測試。**RTM（Requirements Traceability Matrix）**可回答「這項需求由哪些測試驗證？」與「改這條需求會影響什麼？」。變更先做 Impact Analysis，再評估成本與核准，並同步修改相依工件。[ASE-003，PDF p.57–59]

| 自編需求 ID | 設計／實作 | 測試 |
| --- | --- | --- |
| FR-01 查課 | CourseQueryService | TC-01 有結果；TC-02 無結果 |
| NFR-01 查詢延遲 | 查詢與快取架構 | PERF-01 指定負載測試 |

這是示例追溯表，不代表已開發或測試系統。

## 3.6 AI 輔助需求工程

AI 可草擬故事、檢查歧義與衝突、建議追溯關係、模擬利害關係人。**Human-in-the-Loop** 要求人類確認業務規則、例外、法規與資料隱私；模擬訪談不等於真的訪談。語意相似的連結也不等同已證明需求覆蓋。[ASE-003，PDF p.61–68]

## 期中手寫練習重點

給定系統時，先寫 FR，再寫有情境與門檻的 NFR；指出領域規則來源；用五項檢查找缺陷；提出適合的擷取技術與理由。每題應能說出判斷依據，避免只抄英文名詞。
